M8 implementation specification v0.1 — renal physiology and kidney replacement therapy
21 October 2026. Detailed design and synthetic engineering increment, not a real-patient release.

1. Clinical/product boundary
M8 owns kidney assessment and kidney-support clinical records. It references the shared investigation owner, actual medication administrations, M9 collection/volume records, M12 access devices, M7 hemodynamics, M14 nutrition, M17 metabolic context and M18 discharge. It must not duplicate laboratory stores, orders, device episodes, drug formularies or balance totals. No proposal here implies clinical approval. Baseline/history outside the encounter requires explicit authorized longitudinal linkage. Adult ICU is the first proposed clinical validation cohort; all actual eligibility must be known. Children, neonates, pregnancy, transplant, ECMO combinations, burns, cirrhosis and chronic dialysis require applicable profiles rather than a silent default.

2. Data and temporal architecture
Reuse the existing repository/immutable revision/digest/cutoff model. Distinguish clinical occurrence, collection, reporting, recording and ingestion; preserve exact original decimal and timestamp strings. Register schemas for each proposed owned record with additionalProperties false, enumerated availability, bounded arrays/text, maximum payload/interval spans and transport depth. Every unavailable dependent value has a reason; no sentinel zero/NaN. Link unresolved or contradictory associations without inventing a resolution. Validate unit dimensions and analyte species before conversion. Keep source values separate from converted and derived values with method/version/precision. Retain full resolution for comparison; rounding applies only to display. Use explicit interval boundary conventions and union/intersection for coverage; daylight saving and timezone offsets must not change elapsed exposure. Duplicate logical specimen/collection and counter-reset detection precede aggregation. A correction is a successor of one assertion, never a new collection or a physiological change.

3. Versioned inference contract
Each calculation receives requested patient/encounter/review interval/cutoff, population profile, exact input pins and independently signed local policy version. Return per-criterion eligibility, all reasons, exact mathematical result if eligible, display rounding, timing/coverage, limitations and result hash. Inputs may satisfy one criterion while another is unknown; preserve that distinction. No extrapolation of treatment continuity, no unannounced baseline imputation, no latest/favorable-source selection and no global normal flag. Derived values are separate immutable records; source amendment invalidates/requires review of dependents, never rewrites a signed note. The numeric rule catalogs remain disabled until the exact population/device/policy implementation passes independent clinical validation.

4. Clinical profile governance
The official KDIGO page inspected on this date describes the 2026 AKI/AKD update as preparing for publication after public review (S02/S03); the draft is not a production authority. The proposed published baseline is KDIGO2012, locally approved with exact stage boundary tests. Absolute creatinine, relative creatinine, urine and acute KRT criteria stay independent. The proposed registry transcribes cutoffs, not independent approval. All rule implementations require the primary table and footnote review, local specialty sign-off and a change process if new guidance is published. STARRT-AKI (S04), RENAL (S05), ATN (S06), RICH (S07) and society guidance (S08) inform discrete design questions; none supplies a universal patient-specific start, dose, anticoagulation or stopping instruction. Draft status and trial population/applicability appear beside each evidence source.

5. Treatment and drug safety
Prescription, actual delivery, machine setting, measured volume and modeled clearance have different typed fields. A flow rate on an order does not establish running exposure. Model CRRT, IHD/SLED and PD separately. One gross-effluent number cannot establish net patient loss, native clearance, drug clearance or dialysis adequacy. Support interruption/modality/filter/solution change triggers medication-owner review of actual exposure and TDM, including M6. Calcium/citrate interruption is a coordinated human safety workflow; calcium replacement may have an independent indication. A ratio without compatible units, patient-site samples and approved temporal pairing is withheld. All alarms retain native model/channel/sign/clock context and remain bedside device responsibilities. No ClinRx actuator/pump/order interface is added by this increment.

6. Proposed API and storage extension (not implemented)
Use the existing owner authorization and exact state-context pattern. Proposed read routes: GET /patients/{p}/encounters/{e}/renal-review?start=&end=&cutoff=, POST /renal-review/history with exact reference/context; bounded snapshots include available domains and explicit capability flags. Proposed mutations are separate validate/lookup/append routes for baseline selections, assessments, KRT prescriptions and actual segments. Require request id/canonical digest, actor authorization, expected predecessor/context and stale-source review; transactional append and exact replay/absence lookup must reuse existing semantics. Clinical profile execution is a separate protected operation, never inferred from a GET. No real-patient deployment, new clinical write routes or medication/device commands are delivered here. Persist actual clinical reviews only when signed storage, consent/access controls and recovery guarantees exist; session notes are explicitly temporary.

7. Integration plan and existing capability map
Existing RF1 reads bounded creatinine and renal/fluid context with exact history. Existing RF2 provides shared-source charting, source corrections, renal authored review/handover and guarded uncertain-save recovery. Existing recorded weight is shared with the overview; it is not automatically a CRRT dose denominator. Reuse these capabilities. The current creatinine contract lacks guaranteed specimen/collection/quality/withdrawal metadata; source event time and free-text context cannot be promoted to typed missing fields. Existing crrt_context/output_crrt entries are context/net-removal records, not a full prescription, gross effluent, current run state or downtime ledger. The new bedside adapter displays only supported evidence and labels absent structured baseline/AKI/CRRT/citrate capability. New field catalogs are a staged extension plan, not a claim that all fields are ingested.

8. Simple bedside interface
Keep four cards: Kidney status; Urine and collection; Kidney replacement; Next review. Patient/encounter and selected review interval remain visible. Kidney status shows source creatinine count/value and baseline/stage availability without inventing a current result. Urine shows explicit totals/intervals and a completeness/patency gap; no guessed hourly cells. Kidney replacement shows documented context/removal and clearly states when prescription/delivery data are absent. Next review is a deliberate reviewer action with rationale and follow-up plan. A side drawer groups Kidney tests, Urine, Support, Weight and Reviews; it opens exact original source/history, with outside-window/historical/unplaced flags. Do not put the entire design catalog on the bedside screen. No unapproved number becomes a green safety indicator. Current manual assessments are session-only, with immutable evidence pins, stale-draft protection and no chart-save/task-completion claim.

9. Workflow, operational and release safety
Use accessible keyboard navigation, visible focus, screen-reader labels and a narrow-screen layout without horizontal scrolling. During loading/failure mark retained sources historical/unconfirmed and disable recording. A snapshot/patient/source change cancels history reads and invalidates open drafts without losing text or silently rebasing. Reuse existing pending write guards across view switches and retain editor recovery. Backend authorization, least privilege, audited read/write/execute, encryption, protected logs, clinical alert ownership, downtime fallback and recovery belong to release acceptance. Do not infer that synthetic execution-disabled gates are production authorization. Specify institution-specific latency/availability/monitoring SLOs before live activation; stale-data limits depend on clinical workflow, not one universal age. Clinicians must retain an independent urgent-care pathway when data/compute is unavailable.

10. Validation and activation gates
Catalog cases are specifications, not executed tests. Engineering validation includes strict transport, exact references, anti-replay/correction/cutoff isolation, decimal/time arithmetic, coverage/counter resets, stale and race behavior, error recovery and accessibility. Calculation reference examples are educational engineering oracles only and are not used for patient decisions. Independently compare every clinical equation/branch against primary sources and separately implemented gold cases, including exact boundaries and unlike units. Conduct clinician-adjudicated retrospective replay, data-loss/failure injection, prospective silent-mode validation and supervised usability evaluation before authorized pilot. Record false positives/negatives and missed urgent concerns, workflow delays and override outcomes. The release dossier needs named nephrology/ICU, nursing, pharmacy, dialysis engineering and governance approvals; versioned local protocols, signed formulations/device limits, task ownership, rollback and monitoring. Completion of a build or synthetic suite is not clinical validation.

11. Staged implementation backlog
A: source-linked bedside review using current RF1/RF2 and shared catalog (this increment). B: typed baseline/history, specimen completeness, urine collection/patency and population eligibility. C: independently validated, governed AKI/clearance calculations. D: approved prescription and actual CRRT/citrate/downtime/device records with strict accounting and medication/nutrition links. E: delivered-dose summaries, human concern workflows, recovery and durable discharge/follow-up tasks. F: independent clinical validation and controlled activation. Each stage has explicit capability flags; unsupported fields/results remain unavailable. No universal institutional thresholds are filled from memory. M9 fluid aggregation and M6 antibiotic dosing retain their original owners.

12. Policies that remain unresolved
Published guideline/version and population activation; baseline selection/lookback; collection coverage and patency rules; assay/unit/specimen temporal pairing; weight/BSA method; steady-state/drug-label eligibility; CRRT device accounting/dilution/effluent semantics; product/formulation/anticoagulation targets and monitoring; urgent concern thresholds/acknowledgement; prescription/clinical sign-off permissions; trial-off/restart criteria; intermittent/PD adequacy profiles; cross-module accounting; clinical data freshness/SLOs; follow-up ownership and real-patient release. These are requirements to establish, not reasons to fabricate missing data or enable unsafe defaults.
