# Locally saved synthetic handover selections

This opt-in local authoring workspace can explicitly save its handover selections in this browser's localStorage. It does not append a clinical handover, sign off, send or schedule anything. Production protected execution remains disabled. Real-patient use is outside this prototype's scope.

`Save handover locally` stores at most 32 exact kind/ID/revision pins with expected digests, ingestion sequences and original selected cutoffs, scoped to repository/patient/encounter. It stores no clinical payload, narrative or signed state token. The key is `clinrx.synthetic.handover.v1:` followed by a JSON tuple of repository, patient and encounter. Version 1 uses the exact JSON serialization emitted by the application; duplicate/extra members, malformed pins, conflicting scope, duplicate references and oversized storage fail closed.

After reload and fresh API confirmation of scope and disabled execution, the app restores the saved pins. Displayed records come from the verified current API snapshot only when exact reference, expected digest, ingestion and scope match and the saved cutoff is not in the future. An unavailable historical or mismatched pin remains visible as an unavailable saved reference. It is not silently replaced with a successor or an unverified cached payload. Exact historical content can still be inspected through source history separately.

A successful save is reported only after storage readback equals the written bytes. Storage read/write failures preserve the in-memory selections and show an explicit error. Saving detects an already-changed value from another tab and blocks replacement; this is best-effort conflict detection, not a transactional multi-user lock. Unsaved selection changes are not automatically persisted. Explicit removal followed by save can persist an empty selection. Browser storage clearing, another browser/profile or a changed origin does not preserve access to this saved view.

Only handover selection recovery is added. Evidence-entry drafts, uncertain command identities and general durable browser-session recovery retain their previous boundaries; no clinical command recovery is implemented through localStorage. Existing exact lookup/retry semantics are unchanged. No backend contract, database schema, migration, dependency, fixture or execution-gate change is included.
